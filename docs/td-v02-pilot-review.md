## 2. 原六项决定（决定 7、8 见 §9）

### 决定 1　塔锚点：用 `pivot.y = 0.73645`，不用放置偏移

- **等价性：等价。** 偏移法：精灵顶边 y = Y + 67.47k − 256k = Y − 188.53k；pivot 法：顶边 y = Y − 0.73645×256×k = Y − 188.53k（k = 显示缩放，0.295～0.453）。两者在 pivot=1−67.47/256=0.736445 时完全相同；美术给的 0.7364 取整后的误差是 0.0116 帧 px，乘 k 后 ≤ 0.005 px，可以忽略，但让美术写 0.73645（5 位）。【已验证，计算】
- **塔脚几何：美术标的 67.47 px 与成品一致。** 把 `t_jianlou_lv1_idle_01.png` 底边每列的最低不透明像素拟合成椭圆：固定 rx=82.0～82.29（实测最宽行覆盖宽度 164.5 px，rx=82.25）时，ry/rx = 0.817～0.825，椭圆中心在帧底上方 67.6～68.5 px，与 67.47 差 ≤ 1 px（帧）。帧底行 255 有不透明像素，帧宽范围 13..179（中心 96，与 x 锚点吻合）。【已验证，脚本拟合；不固定 rx 的自由拟合给出 ry/rx=0.86，但 rx、ry、yc 互相牵连，拟合质量与固定法接近（rms 0.20 对 0.28 px），不作为依据】
- **为什么选 pivot：**
  1. Phaser 4.2.1 里 JSON 的 `pivot` 会覆盖手动 `setOrigin`：`Texture.js` 的 setFrame、`AnimationState.js:1600` 每次换动画帧都执行 `setOrigin(frame.pivotX, frame.pivotY)`。所以“JSON 写 (0.5,1) + 客户端自己 setOrigin(0.5,0.7364)”不可行，会被下一帧覆盖；放置偏移则要客户端为每个塔帧、每档外观带一个常数。pivot 写进 JSON 就是唯一来源。【已验证，读源码 `node_modules/phaser/src`；实机运行未测，见 U1】
  2. 客户端现有约定本来就是“塔脚底 = 塔基中心”：`battle.ts:186-189` 的 `at(tower.x, tower.y)`、`hit.ts:42` 的塔体矩形底边 `bottom = foot.y`、射程圈、血条、环形菜单都以它为准。pivot 法让 `sprite.y` 恰好等于这个点，客户端不用任何偏移。【已验证，读 PR #2 源码】
  3. 深度排序不受影响：`depth.ts:7` 的 `depthKey` 用的是世界 y（塔基中心行 r+0.5），不读 `sprite.y`。若用偏移法并有人改成按 `sprite.y` 排，塔会被当作“近 0.37 格”，把站在塔基边缘的敌人盖住。【已验证，算术：0.9×0.5×0.82=0.37 格】
  4. 缩放/建造动画（弹出、选中放大）以 origin 为中心。origin 在占地中心时塔原地长大；在前沿时中心会漂移 ≈ 0.1×67.5×k ≈ 2～3 设计 px。【已验证，计算】
- **配套改动（美术）：** 所有塔帧 `pivot = {x:0.5, y:0.73645}`；`firePoint.fromAnchorPx` 改成相对占地中心：(25.1, −212.8+67.47) = **(25.1, −145.33)**；`groundCenterFromBottomPx` 字段保留作校验。其余塔档位（Lv3、A/B 档）规则相同：pivot.y = 1 − ry/帧高。敌人保持 (0.5, 1.0)（脚底中心）。统一规则写成一句：**锚点 = 单位占地中心在帧里的位置，敌人是脚底中心，塔是占地椭圆中心。**
- **同时记一笔：** 视觉塔身只有占地中心以上 176.5 px = 0.965 格高（帧顶不透明行 12，见 N4），客户端 `hit.ts:51-54` 的 1.4 格高度和血条/等级牌的 `p.y − size.h − 8` 要改成读帧数据。

### 决定 2　动作名 `attack` 可以用

- 与 Phaser 动画 key 不冲突：动画 key 是 AnimationManager 里的全局字符串，美术给的是 `t_jianlou_lv1_attack`，带塔 id 和档位，不会撞；帧名 `t_jianlou_lv1_attack_01` 在纹理帧命名空间，与动画 key 是两个空间。【已验证，读 `AnimationState` / `JSONHash.js`】
- 与客户端命名不冲突：PR #2 里没有任何 `anims` / `.play(` 调用（`git grep`，当前渲染全是矩形占位）；`attack` 只作为英雄数据字段名出现（`catalog.ts:78`，值是 `'single'|'pierce'|'splash'`，`sim.ts:1631-1682`），是另一个命名空间；sim 事件类型里没有 `attack`（事件有 `shot`、`rout`、`down`、`skill`、`fire`、`hold`…，`sim.ts` 里 `type:` 统计）。【已验证】
- **动作词表定稿（写进规格 3.1）：** `idle`、`walk`、`attack`、`skill`、`die`（敌人、Boss 溃散，对应事件 `rout`）、`down`（武将、枪兵倒下，对应事件 `down`）。美术建议的溃散用 `die` 同意。
- 触发映射：事件 `shot`（`sim.ts:1130`）→ 播放该塔 `*_attack`，弹道在 `releaseFrame`（第 2 帧）出现，约比事件晚 83 ms；`rout` → `*_die`。注意 `shot` 事件只带塔 id 和坐标，没有目标坐标，弹道要朝哪打需要 sim 补一个 `tx,ty`（小改，见 N6）。
- 速度：箭楼 Lv1 `aps=2`（`catalog.ts` 行 `row(1,'',10,2,…)`）→ 间隔 500 ms，攻击动画 4 帧@12fps=333 ms，放得下。连弩台技能攻速×2 → 间隔 250 ms，放不下，所以攻击动画的 timeScale 要跟攻速走：`timeScale = clamp(0.333 × aps, 1, 3)`（动画用时 ≤ 间隔的 2/3）。【已验证，算术；运行效果未验证】

### 决定 3　乱兵行走：12 fps 起步，timeScale 跟移动速度

> **§9 已更新口径。** 像素步幅未变（一步两脚质心距仍是 27.67 px，webp 未重导），但 `pxPerCell` 从 213.33 改为 145 后，每周期从 0.26 格变成 **0.382 格**，零滑步从 28.8 fps 降到 **19.6 fps**。试点仍定 12 fps，脚滑从 58% 降到 39%，不要求美术返工。公式、1×/2× 数值、timeScale 钳制、全量版步幅目标见 **§9 决定 7**。下面保留初评时的像素测量，格数已作废，不要再用。

- **像素步幅（仍有效）：** 侧向帧 1、4 支撑相，两脚连通域质心距 27.67 px；6 帧一个周期=两步，周期 55.33 px。【已验证】
- **客户端做法（与 §9 一致）：** `scene.anims.globalTimeScale = 倍速(1 或 2)`；每个敌人精灵 `anims.timeScale = clamp(v实际 / v参考, 0.5, 1.6)`，v 参考 = 该单位基础速度（乱兵 1.25，来自 `catalog.ts` / `levels.json` `rules.enemy_speed`）。两者相乘 ≤ 3.2（≤ 38 fps）。减速时脚步跟着变慢；暂停时 `anims.pauseAll()`。动画不进 sim。

### 决定 4　k=0.82 定稿

- 一致性：方案 §2.2（k=0.82，= sin55°）【已验证，读文档】；PR #2 `view.json` `"k": 0.82`、`"kz": 0.57`（= cos55°）【已验证】；美术 `bg_M1.json` `projection.k=0.82, kz=0.57`、`padSpec.ryOverRx=0.82`【已验证】；背景塔基 ry/rx：32.0/39.0=0.821、45.8/55.9=0.819【已验证】；塔鼓座成品拟合 ry/rx=0.817～0.825（见决定 1）【已验证】。
- 代价：比 B 概念图（量出来约 0.5）更“俯视”，美术 NOTES §3-4 已说明。射程椭圆用 0.82 与 PRD 一致，不再改。冻结 `view.json`：S0=72、k=0.82、kz=0.57、sFar=0.75、sNear=1.15、Y0=150，之后改动要同时重出背景和塔基。

### 决定 5　不做 1080×2340 高屏背景

- 技术上没有问题：PR #2 的 `viewport.ts` 里 `designW/H` 固定取 `VIEW.frameW/H = 720×1280`，`cssScale = min(vw/720, vh/1280)`，高屏手机只会在 #fit 外留黑边，不会拉出更多设计高度。背景只需要覆盖 720×1280 设计帧。【已验证，读 `viewport.ts`、`view.json`】
- **相关发现（有益）：** 客户端 canvas 只是地图槽 `mapW×mapH = 720×960`，放在设计帧 y=96～1056（`view.json` `mapTop:96`）。美术背景覆盖 0～1280，其中 y<96 和 y>1056 共约 25% 客户端永远画不到。可以直接裁成 1080×1440（设计 y 96～1056）→ 纹理 8.29 MB 降到 6.22 MB，省 2.07 MB，也少一块图；不裁也行，客户端必须按 y 偏移 −96 放置（见 §6）。【已验证，计算】
- 视觉上世界行 0 在 canvas y=54，行 16 底边在 canvas y=951.4（`worldToCanvas`，`Yg(0)=150, Yg(16)=1047.4`），都在地图槽内。

**6c 影子：独立 L1 贴花层，不烘进帧**

- 理由：① 烘进帧后 `flipX` 会把右下影子翻到左下，违反“左上来光”（侧向左走用 flipX）；② 行走时髋部上下 3.8 px，烘焙的影子会跟着晃，贴花留在地面；③ 烘焙影子会让帧不透明面积增加，trim 收益变小，且影子会盖到前面的单位上（L2 排序后影子在近处单位身上）；④ 飞行单位（鹰）要地面影子，必须独立；⑤ 美术 NOTES §3-10 也是这个做法。【理由已论证；①②未用 Phaser 实测】
- 规格（取自美术 `compose_preview.py`）：通用 `fx_shadow` 一张软边椭圆（64×32，WebP，放 atlas_fx_0），深褐 (20,14,6)，不透明度约 0.43（110/255），高斯模糊约 2 px@1080；宽 = 0.40×72×s(y) 设计 px（rx=0.20 格），高 = 宽×0.82×0.55，偏移约右 1.3、下 0.7 设计 px；乱兵用此值，Boss、刀盾兵按体宽等比放大。
- 混合模式：用 NORMAL（普通 alpha），不要 MULTIPLY。MULTIPLY 会在 L1/L2 之间多一次混合状态切换，普通 alpha 与美术预览一致。
- 绘制调用：所有影子同一张纹理、同一混合模式、同一层 → 一个批次。每个地面单位多 1 个精灵（60 敌 + 16 塔 + 英雄/枪兵约再加 60～80 个，总精灵 ≈ 170 个，方案原写 ≈ 90 个，需更新）。塔的接触阴影已烘在背景里，塔不需要贴花。**L2 里敌人/塔/英雄来自不同图集，按深度交错会打断批次**；Phaser 4 是否能多纹理合批、实际 draw call 数，需要真机或 debug 面板数一次（目标 ≤30，上限 40）。【未验证，见 U3】

## 6. 可直接交客户端的接入要点

### 6.1 加载清单（战斗场景 preload）

| key | 文件 | 说明 |
|---|---|---|
| `atlas_enemy_0` | `atlas/atlas_enemy_0.webp` + `.json`（JSON Hash） | 乱兵 f×6、s×6 |
| `atlas_tower_0` | `atlas/atlas_tower_0.webp` + `.json` | 箭楼 Lv1：idle 1 + attack 4 |
| `bg_M1_0`、`bg_M1_1` | `map/bg_M1_0.webp`、`bg_M1_1.webp`（单图） | 背景上、下半；`bg_M1.json` 的 `tiles[]` 给分块偏移 |
| `fx_shadow` | 新增，美术补 | 通用影子软椭圆，放 atlas_fx_0 |

- 用 `this.load.atlas(key, webp, json)`；Phaser 4.2.1 的 JSON Hash 解析器会读 `pivot`（`textures/parsers/JSONHash.js:80-87`）。【源码已确认】
- M1 和 M1b 共用同一份背景；M1b 把两块背景都 `flipX`，并保持块序。
- 战斗结束 `textures.remove` 释放；图集和背景只在进入战斗时加载（首屏不加载）。
- 游戏配置加 `render: { mipmapFilter: 'LINEAR_MIPMAP_LINEAR' }`（只对 POT 图集生效；背景不受影响）。

### 6.2 锚点 / origin

- **所有帧用 JSON 里的 pivot，客户端不再手动 `setOrigin`**（会被动画帧更新覆盖）。敌人 pivot=(0.5, 1.0)；塔 pivot=(0.5, 0.73645)（美术按决定 1 重出）。
- `sprite.setPosition(at(x, y))`，其中 `at` 即 `worldToCanvas`；塔用塔基中心（`tower.x, tower.y`），敌人用插值后的脚底世界坐标。不加任何偏移。
- 显示缩放：敌人 `scale = s(y)·72 / 145`，塔 `scale = s(y)·72 / 182.857`（**必须读 JSON `meta.td.pxPerCell`，不要写死**；乱兵已从 213.33 改为 145，见 §9）。`s(y)` 按脚底 y 连续取值，行走中每帧更新。
- 侧向帧朝右，向左走 `flipX = true`；有自定义 pivot 时 Phaser 4 在原地镜像（`TransformerImage.js:131-143`，x 锚点 0.5=帧中心）。方向选择：|Δy| ≥ |Δx| 用 `f`，否则用 `s`，路线只有向下、向左、向右（方案 §3.1 已验证；M1.json 路径里 c/r 只增或横移），换向时保持上一个方向避免抖动。
- 发射点：`firePoint.fromAnchorPx = (25.1, −145.33)`（B1 修好后），乘塔的显示缩放，加到塔基中心。

### 6.3 动画 key 与 fps

| 对象 | key | 帧 | fps | repeat |
|---|---|---|---|---|
| 乱兵前走 | `e_luanbing_walk_f` | `e_luanbing_walk_f_01..06` | 12 | −1 |
| 乱兵侧走 | `e_luanbing_walk_s` | `e_luanbing_walk_s_01..06` | 12 | −1 |
| 箭楼待机 | `t_jianlou_lv1_idle` | `t_jianlou_lv1_idle_01` | 1 | −1 |
| 箭楼攻击 | `t_jianlou_lv1_attack` | `…attack_01..04` | 12 起，`timeScale=clamp(0.333×aps,1,3)` | 0（播完回 idle） |

- 动画从 JSON `meta.td.anims` 读，用 `this.anims.create` 注册，帧写成 `{key:'atlas_enemy_0', frame:'…'}`。
- `anims.globalTimeScale` = 倍速；敌人 `anims.timeScale = clamp(v实际/refSpeed, 0.5, 1.6)`，乘积 ≤ 3。动画不进 sim。
- 攻击：收到 `shot` 事件播 `*_attack`；弹道在第 2 帧（`releaseFrame`）出现。死亡：`rout` 事件播 `*_die`（全量版）。

### 6.4 深度层（统一常量，修 B2）

| 层 | 内容 | depth |
|---|---|---|
| L0 | 背景 2 块 | 0 |
| L1 | 影子贴花 | 10；射程椭圆/选中圈/吸附圈 20 |
| L2 | 塔、地面敌人、英雄、枪兵、城门 | `depthKey(y, kind, x, id)`，范围 [0, 17,000,000)（y ≤ 16） |
| L3 | 被挡住时的剪影 | 20,000,000 + 同 key |
| L4 | 飞行（鹰） | 30,000,000 + y×1,000 |
| L5 | 弹道 | 40,000,000 |
| L6 | 特效 | 50,000,000 |
| L7 | 血条、等级牌、飘字、金币 | 60,000,000 起 |

- 排序规则不变：脚底世界 y 越大越晚画；同 y 按 建筑 < 英雄 < 枪兵 < 敌人，再按 x、id（美术预览与 `depth.ts` 一致）。
- 塔用塔基中心行（r+0.5）作 key，不用 `sprite.y`。
- 血条等 L7 不要再画在 depth=2 的 `fx` 图形里。

### 6.5 影子层

- 地面单位每个配一个 `fx_shadow` 精灵，depth=10，NORMAL 混合，α≈0.43，位置 = 脚底 + (1.3, 0.7)·s 设计 px，宽 0.40×72×s，高 = 宽×0.45；随单位创建/销毁；飞行单位影子留在地面（脚下投影点），塔不画（背景已烘接触阴影）。
- 单位死亡/溃散时影子随单位淡出。

### 6.6 坐标常量来源（只有一份）

- `src/data/view.json`（S0=72、k=0.82、kz=0.57、CX=360、Y0=150、sFar=0.75、sNear=1.15、span=15、mapTop=96、mapW=720、mapH=960、frameW=720、frameH=1280、hitFloorPt=22）是投影常量的唯一来源；美术 `bg_M1.json` 的 `projection` 抄自同一组数。常量变更要同时重出网格参考图、背景和塔，并跑第 3 节的核对脚本。
- 塔基世界坐标来自 `src/data/maps/M1.json`、`M1b.json`（格中心 c+0.5, r+0.5）。
- 背景放置：背景坐标系是整张设计帧 720×1280，client canvas 是其中 y=96 起的 720×960 槽，所以背景块位置 = (0, tile.y·(2/3) − 96)，缩放 2/3（1080→720）。若采用 N1 裁剪版（只含 y 96～1056），则位置 (0, 0)。
- 点击：塔基椭圆命中、半径 0.5 格（行 0～3 ×1.3，不小于 44 pt）沿用 `hit.ts` 现有逻辑，塔体矩形改读帧元数据（N4）。

### 9.2 决定 7　帧率与 timeScale：试点仍 12 fps，接受 39% 脚滑；全量版加大步幅，不提高基准帧率

零滑步公式（与美术 JSON `noSlideFrameRate` 一致）：

```
fps_zero(v) = N × v / C
```

其中 N=6（一个周期的帧数），C=`walkCycleCells_s`=0.382，v 是该单位当前地面速度（格/秒）。用实测 0.3816 算出的结果与 0.382 相差不到 0.03 fps，以下按 0.382。【已验证，算术】

乱兵 v=1.25（PR #2）：

| 倍速 | v（格/s） | 零滑步 fps | 12 fps 下动画速度 | 脚滑比例 |
|---|---|---|---|---|
| 1× | 1.25 | **19.63**（约 19.6） | (12/6)×0.382=0.764 格/s | **38.9% ≈ 39%** |
| 2× | 2.50 | **39.27**（约 39.3） | 1.528 格/s | 仍是 39%（比例不变） |

其他单位若沿用同一周期（帧还没有，仅作对照）：刀盾 1.15 → 18.1 / 36.1 fps；轻骑 1.50 → 23.6 / 47.1，冲刺 2.25 → 35.3 / 70.7；山贼 1.92 → 30.2 / 60.3。2× 时山贼、轻骑冲刺会顶到或超过 60 Hz，出现频闪。——所以**不能靠把基准帧率提到 20 来消滑步**。【已验证，算术；其他单位的周期【未验证】】

**试点决定：基准帧率保持 12 fps，不要求美术改动画。**

- 图集 `meta.td.anims` 已是 12 fps，webp 未动；改帧率只是客户端播放参数，但把基准提到 19.6 会让 2× 到 39 fps，更快的敌人以后更危险。12 fps 下脚滑 39%，比初评的 58% 已经明显改善，Q 版可接受。
- 客户端（与决定 3 相同，只更新钳制上限）：

```
anims.globalTimeScale = 倍速          // 1 或 2
sprite.anims.timeScale = clamp(v实际 / v参考, 0.5, 1.6)
globalTimeScale × timeScale ≤ 3.2     // 有效帧率 ≤ 38.4，低于 60 Hz
```

v参考 = 该单位基础速度（乱兵 1.25，来自 `catalog.ts` / `levels.json`，建议美术在 `meta.td` 补 `refSpeed`，没有就读目录）。减速时脚步变慢，不再原地划水；暂停用 `anims.pauseAll()`。动画不进 sim，不影响回放确定性。

- 不要用 `timeScale = fps_zero(v)/12` 在客户端“加到零滑步”：乱兵 1× 有效 19.6 fps 可以，但同一套公式用到山贼 / 轻骑冲刺，2× 会到 60～70 fps。消滑步靠加步幅，不靠加帧率。

**全量版目标（写给美术，不挡试点接入）：**

- 下限：每周期步幅 **≥ 0.50 格**（12 fps、v=1.25 时脚滑 ≤20%）。
- 理想：每周期 **0.625 格**（= 6×1.25/12），12 fps 正好零滑步；2× 有效帧率仍是 24，不会频闪。一步 = 0.31 格，约为 0.8 格身高的 39%，接近自然步态（现在一步 0.19 格，只有身高的 24%）。
- 实现：加大腿摆角或步幅，**不加帧**。帧预算不变。效果【未验证】。

对客户端接入：**无阻塞影响。** 动画 key、12 fps、timeScale=v/v参考 的接法与初评相同，只是脚滑数字从 58% 改为 39%。唯一要改的是显示缩放读 145，见决定 8。

### 9.3 决定 8　帧保持 128，不改 160/192/256

规格含义核对。【已验证，与 `td-tech-v0.2-25d.md` §3.1 一致】

- **2.53 倍** = 最近一行 s=1.15 × renderScale 2 × 1.1 余量，即“1 设计 px 对应至少 2.53 资源 px”。0.8 格身高在 s=1.15 时是 0.8×72×1.15=**66.24 设计 px**，要 66.24×2.53=**167.6 资源 px**。
- **1.75 倍** = 现有实心身高 116 / 66.24 = **1.751**。美术 NOTES §3-13 的算法正确。达到规格还差 52 px；116 只有目标的 69%。

落到 framebuffer 上（更关键；`renderScale = min(2, roundQuarter(cssScale×dpr))`，见 PR #2 `viewport.ts`）：

| 位置 | rs=1.0（如 360×800、dpr 2） | rs=1.5（如 iPhone 12，390×844、dpr 3） | rs=2.0（如 720×1280、dpr 2） |
|---|---|---|---|
| 远处 s=0.75 | 43.2 px，资源/画面=2.69，余量充足 | 64.8 px，1.79 | 86.4 px，1.34 |
| 中间 s=1.00 | 57.6 px，2.01 | 86.4 px，1.34 | 115.2 px，1.007（刚够） |
| 近处 s=1.15 | 66.2 px，1.75 | 99.4 px，1.17 | **132.5 px，0.876（欠采样 12%）** |

只有“近处一行 + renderScale=2”会略软；主流手机是 rs=1 或 1.5，都不欠。远处仍然缩小，mipmap 仍要开（决定 6）。【已验证，计算；观感【未验证】】

若要凑满 2.53 倍：把整帧按比例放大后，盔顶身高 = 116×(边长/128)。160 帧 → 145 px，145/66.24=2.19，**仍不够**；192 帧 → 174 px，174/66.24=2.63，才刚过线。所以“补余量”的最小档是 192，不是 160。

纹理内存（解码 RGBA，估算）：

- 现在 128：第一章敌人约 112 帧，trim 后约 0.83 Mpx，一张 2048²（16.8 MB）装得下，符合方案 §3.3。
- 改 192：面积 ×2.25，约 1.87 Mpx，仍是一张 2048²。
- 改 256：面积 ×4，约 3.3 Mpx，加上刀盾/轻骑和枪兵，可能要第二页（+16.8 MB），总预算仍 < 110 MB，但没必要。

**决定：帧保持 128。** 理由：webp 不用重导；欠采样只出现在少数 rs=2 近处，软 12%，Q 版可接受；要达标至少得 192，投入与收益不相称；内存不是约束，约束是重画成本。PRD V0.2.1 已写“帧保持 128”，本决定与之对齐。近处发软列入 U4，真机看过再决定要不要补 192。【内存为估算】

对客户端接入：**无阻塞影响，但显示缩放必须改读 145。** 若写死 213.33，乱兵会被画成 0.8×145/213.33≈0.54 格高，回到改口径之前。读 `meta.td.pxPerCell` 即可。占位矩形建议改为约 0.5×0.8 格（N2），不挡精灵接入。
